# D45. 码表缓存 `stock_codes.conf` **由 `--save tdx` 从 8.3 `stock_list` 导出** —— 2026-10-15

- **编号**：D45
- **日期**：2026-10-15
- **索引**：[DECISIONS.md](../../DECISIONS.md) —— `grep D45 DECISIONS.md`，或直接开这个文件

**背景**（用户）：「处理一下更新 `~/.GolemQ/datastore/cache/stock_cn/stock_codes.conf`
在每天 `--save tdx` 成功更新 `stock_list` **有增量后**更新」。

### 一、这个文件是什么（先纠正一个叫法）

它不是"白名单"，是 `easyquotation` 全市场快照（`BaseQuotation.market_snapshot`，
即 `--sub l1_tencent` 的数据源 —— ⚠️ 原文并列写的 `l2_tencent` **已于 2026-10-15 整条删除**，见 D47）的**枚举源** ——
`gen_stock_list()` 按 `max_num` 把它切页，逐页 HTTP 取回。

**实测它此前已严重滞后**（2026-10-15）：

| | 码数 | 备注 |
|:--|:--|:--|
| 缓存 `~/.GolemQ/.../stock_codes.conf` | **5,186** | 还留着 `300114`（已退市/换码） |
| 8.3 `stock_list`（权威） | **5,580** | pytdx 主源 + tdxaidata 补北交所 352 只 |

差的正是 2026 年新上那批。而**症状是完全静默的**：订阅器照跑、照签到，
只是实时集合里少了那几只。

**为什么滞后**：唯一的刷新口 `helpers.update_stock_codes()`（敲 `shdjt.com`）
**全树零调用**，且换了 `encoding`/建目录都没有。

### 二、决定：从 8.3 导出，**不**敲第三方站点

* 新增 `refdata_save.refresh_stock_codes_cache()`：读 `_authoritative_codes()`
  （= `stock_list` 的 distinct code）→ 与缓存比对 → 有增减才写。
* **不新增取数逻辑**：`--save tdx` 刚刚把 `stock_list` 刷进 8.3，那份就是本次的权威名单
  （pytdx 主源 + `_supplement_stock_list` 用 tdxaidata 补上 pytdx 枚举不到的北交所）。
  从库里导出 = **零网络**、与本流程同源。
* **拒绝的方案：复用 `update_stock_codes()`**（即"修好旧函数"那条路）。
  实测 `shdjt.com` **19.1 秒**才回来（`timeout=15` 下时好时坏、`https://` 直接拒绝连接），
  且它**不覆盖北交所**。拿它做每日刷新 = 给 `--save tdx` 挂一个不稳定的外网依赖，
  而库里那份**更全、且刚到。**
  但它的**写法**收敛进 `helpers.save_stock_codes()`（见下），所以"平行实现"没有分叉。

### 三、写盘的两条护栏

| 护栏 | 为什么 |
|:--|:--|
| **`MIN_STOCK_CODES = 1000` 之下拒写** | 缓存空了 ⇒ `market_snapshot()` 一台标的都不取 ⇒ **实时集合每天是空的**，且不报错。宁可留旧表。 |
| **原子写**（`.tmp` → `os.replace`） | 读方读**同一个路径**；写一半被中断（Ctrl-C / 磁盘满）留下半个 JSON ⇒ `use('tencent')` 当场抛 ⇒ **L1/L2 两个订阅器一起起不来**。 |

另：`helpers` 里那个文件曾有**两份写法**（`update_stock_codes` 自己 `open(...,'w')`，
既没建父目录也没写 `encoding`）。现已收敛到 `save_stock_codes` —— 平行实现不会报错，
只会分叉（与 `fq.py` 那次同一个教训）。

### 四、触发条件（调用方 `cli/commands/save.py` 的契约）

两条**同时**成立才落盘：

1. `stock_list` 本次 **`status == 'ok'`**（真的取到行并写库）。
   ⚠️ 刷新闸拦下的 `cached` **不算**"成功更新"（没碰源）；
   `skipped`（源返回 0 行）/ `failed` 更不算。
2. 码表**有增减** —— 增删皆空时不写盘（每日跑大多数天是不变的）。

`--save-collections etf_list` 这类没带 `stock_list` 的跑法自然跳过。

### 四之二、输出的 `-v` 口径（2026-10-15 用户补）

**成功是静默的**：「码表缓存已更新：N 只（+a / -b）」这句**只在 `-v` 下打**
—— 与参考数据的**刷新闸**那句、逐集合状态表**同一口径**：
都是实现细节，不是每次运行都要看的（用户 2026-10-09 就明确定过这条）。

⚠️ **两个例外，不跟 `-v` 走**：**拒写**（码数低于 `MIN_STOCK_CODES`）与
**失败**（调用方的 `except`）—— 那两种情况意味着「这次没写 / 写坏了」，
静默会被读成"写成功了"。有一条用例专门钉这两个例外。

### 五、本次**没做**的

* **ETF 与指数没进这张码表** —— 见 **D46** 第三节（它们腾讯**供得了**，只是没被枚举）。
* 没写成独立的 banner 节点：它没有"取数"这一步，硬塞一行会留一个点不亮的灰点
  （`PITFALLS.md` P22 同款的记账问题）。
