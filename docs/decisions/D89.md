- **测试**：`test_cases/analysis/test_zen_ols.py`、`tools/diagnostics/probe_zen_ols.py`

## 为什么重建而不是照搬

老树 `ZEN.OLS_TIMING_LAG`（`ZenOLSLag`）的生产链极长：

```
MA30范数lag + DEA归零lag → zen_mapower30_predict（聚类）→ 段边界
→ calc_slice_with_wavelet → calc_slice_with_cluster_grouped(margin=8)
→ 每段 find_peak_vextors + zen_in_ols_v2_func(LIS/LDS) → JX/SX duration → event lag
```

要搬得连带 `zen_mapower30_predict` / `calc_slice_with_wavelet` /
`calc_slice_with_cluster_grouped` / `LIS` / `LDS` / `get_index_of_peaks` /
`find_peak_vextors` 一起，且它**自带未来函数**（对整条历史一次算完，段尾信息
回流段首）。用户 2026-11-22 定：**重新创建、避开这些依赖**。

## 新设计

```
段  = ZenPivotLag 的符号相同的连续 bar（>0 中枢内 / <0 中枢外，NaN ffill 不造新段）
段内：low 的峰点 → LIS（最长递增子序列）→ 标 +1
      high 的峰点 → LDS（最长递减子序列）→ 标 -1
JX = Timeline_duration(cross == +1)；SX = Timeline_duration(cross == -1)
ZenOLSLag = calc_event_timing_lag(where(JX < SX, +1, -1))
```

只保留**决定信号的那一步**（段内 LIS/LDS），分段换成我们已经落库、且语义天然的
中枢 lag：`ZenPivotLag > 0` = 已在中枢内 N 根（盘整），`< 0` = 已离开中枢 N 根
（趋势，也就是老树说的「波浪」）。

参数（用户 2026-11-22 定）：`in_pivot_marks=True`（中枢内也判二乘趋势）、
`min_peak=2`、峰点口径 **CZSC**（见下）。

## 峰点口径：两种都测了，选 CZSC

2024-06 ~ 2026-11、60min、因果口径、含中枢：

| code | 口径 | 交叉数 | lag 符号翻转 | 距段边界中位 | \|lag\| 中位 |
|:--|:--|--:|--:|--:|--:|
| 000711 | scipy 相邻极值 | 145 | 77 | 46.0 根 | 26 |
| | **CZSC 分型** | **43** | 35 | 132 根 | **49** |
| 600519 | scipy | **561** | 260 | 24.5 根 | **9** |
| | **CZSC** | **50** | 43 | 30 根 | 40 |
| 603366 | scipy | 416 | 189 | 25 根 | 10 |
| | **CZSC** | **50** | 43 | 42 根 | 42 |

1. **密度**：scipy 在 600519 上每 2.3 根 bar 一次交叉，`|lag|` 中位 9 根 —— 信号
   互相覆盖，等于噪声；CZSC 每 24~33 根一次，`|lag|` 中位 40~49。
2. **因果化代价**：scipy 因果版翻转数是事后的 **2 倍**（260 vs 142），说明它严重
   依赖未来；CZSC 两版接近（43 vs 45），因果化几乎不掉信息。
3. **同源**：段边界来自 CZSC 中枢，峰点也用 CZSC 分型，两者不会互相打架。

`in_pivot_marks=True` 是决定性的：只标中枢外时，000711（75% 时间在中枢内）
2.5 年只有 **10 次**交叉、`|lag|` 中位 689 根 —— 等于没信号。

## 因果性（本项目最容易踩的坑）

* **峰点**：CZSC 分型要等后续 bar 确认，`frame_context` 记录每个分型的
  `known`（确认 bar），因果模式下 `cross` 打在**确认 bar** 上；
  `scipy` 口径同理（`argrelextrema` 判 i 是不是极值需要 i+1 ⇒ `known=i+1`）。
  ⚠️ 这一点第一版写错了（当成当场知道），被 `test_lag_matches_truncated_run` 抓到。
* **分段**：⚠️ **不能用「整帧一次 CZSC」**。整帧的笔/中枢会被后续 bar 修订，
  实测 601595 在 T=3000：截断算 +3、全量算 -129 —— 与 D84 同一个未来函数。
  生产路径改成**逐 target 用 ≤T 的 2160 根窗口**（与 `pivot_stats` 同口径），
  实测中间目标与最后一根都**逐值一致**。
* **段头 NaN**：开头的 `ZenPivotLag` 为 NaN 时记「未知段(-1)」不参与标记 ——
  用 `bfill` 补会吃未来的值。

## 落库位置：`--review`，不是 compact/mainstream

| 路径 | 结论 |
|:--|:--|
| `--strategy review` | ✅ 逐码特征生产；`ZenPivotLag` 就在同一步产出，同一趟算 |
| `--strategy compact` | ❌ 文件开头写明「只读，不落库」，是派生层 |
| `--strategy mainstream` | ❌ 横截面聚合层，逐码只取 4 列投票；再加 CZSC+LIS 会拖慢本来 3~6 小时的跑批 |

落库后：`reality_attach._attach_60min` 按 `HOUR_ZEN_COLUMNS` 自动 join；
`mainstream` 若要用于投票，也是**读这一列**，不自己算。
盘中要现算用 `--review-runtime`（`compute_runtime`，零落库）。

## 与老树的差异

**数值不同，这是刻意的**：分段依据（中枢 vs 聚类）、峰值口径、因果处理都变了。
本列是**新定义**，不与老树对拍；正确性靠「因果性 + 段边界合理性 + 分布」三条验证。

## 遗留

* 没有为「中枢内段」单独设计标记规则（目前与中枢外同一套 LIS/LDS）；
* `min_peak=2` 未做敏感性分析；
* 尚未回填历史（`--strategy review` 跑起来会算；已落库的行需要 `--force` 才会补这一列）。


## 附：流式口径（用户 2026-11-23 选定，替换 D89 初版的逐窗口）

初版是「**每个 target 重建一次 2160 根窗口的 CZSC**」：因果、前缀稳定，但成本
`O(目标数 × 窗口)` —— 9,800 根要 ~12 分钟/码，全库 18M 行 ≈ **11 小时**。

现改为**流式**：一遍 `CZSC.update` 走到底，第 T 根只看过前 T 根：

```python
czsc = CZSC(bars[:1]); conf = {}
for i, bar in enumerate(bars[1:], 1):
    czsc.update(bar)
    if 末笔 fx_b 变化:            # 分型确认事件（9,804 根约 1,060 次）
        conf[key] = bar.dt
        重算最近 2160 根的「中枢 lag」（calc_pivots + causal_pivot_series）
        在当前段前缀上跑 LIS/LDS，判断新分型是否推进趋势 → cross[i]
jx/sx = Timeline_duration(cross == ±1); lag = calc_event_至…
```

* **成本**：`O(总 bar 数)`，实测 9,804 根 **5.1s**（CZSC 回放只 0.2s，其余是
  1,060 次中枢重算 × 5ms）；全库回填从 ~11 小时降到 **~15 分钟**；
* **口径变化**：历史从「2160 滚动窗口」变成「从帧头累积」。数值与初版**不同**
  （601595：48%→54% 正、翻转 151→267、\|lag\| 中位 58→25），这是刻意接受的；
* **因果**：`CZSC.update` 天然只看过去 ⇒ 前缀稳定，用例
  `test_zen_ols.py::TestStreamingCausality` 钉住（截断 T=150/260/419 逐值一致）。

### 除权会不会破坏它？（用户 2026-11-23 追问，已实测）

**不会。** review 取数 `if_fq='qfq'`（前复权），一次除权 = 整条历史乘一个常数；
实测整体 ×0.5 / ×2.0 / ×0.1，9,804 行 **逐值完全相同（最大差 0）**。原因：
CZSC 的包含/分型判定是纯比较、LIS/LDS 比的是序、产物是「距事件的 bar 数」——
全程无量纲。

保留边界说明：

* 若读的是 `bfq`，除权是**真实跳空**，CZSC 会在缺口造假分型 —— 那是**输入口径**
  问题，不是流式的错；
* 唯一对量纲敏感的是 ChipDist（`minD=0.01` 绝对分箱），它靠自己的 `adj` 还原、
  `RETURN_COST5` 又是对数比值，已单独处理。

用例 `test_zen_ols.py::TestScaleInvariance` 把这条钉死：谁引入绝对价格阈值，
立刻红。
