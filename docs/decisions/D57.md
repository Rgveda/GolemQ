# D57. 消息推送分层：`agents.channels`（渠道）与 `supervisor.alerts`（告警）

- **编号**：D57
- **日期**：2026-10-20
- **索引**：[DECISIONS.md](../../DECISIONS.md) —— `grep D57 DECISIONS.md`，或直接开这个文件

**背景**：`agents/messenger.py` 与 `supervisor/messenger.py` 同名但职责不同，且后者
私写了一份 Server酱发送 —— 两套实现**已经分叉**：

| 项 | `agents.messenger` | `supervisor.messenger` |
|:--|:--|:--|
| 定位 | 渠道适配器 + 配置 | 告警策略 + 扇出 |
| Server酱编码 | JSON | **form** |
| `sctp` key | 支持（独立域名） | **不支持**（仍打旧域名） |
| 级别语义 | 无 | `level` 字符串 |
| 全局实例 | 无 | `global_messenger` |

另有一批零调用 API（`configure_*`、`custom_webhooks`、`send_test_message`、
`configure_global_messenger`）与零引用 `MessageLevel`；钉钉告警在 `send_alert`
里本就整段注释，只有死代码 `send_test_message` 能到达 `_send_dingtalk`。

---

## 一、决定

1. **保留两层，不合并成一个模块**：
   * `agents/messenger.py` → **`agents/channels.py`**：协议、鉴权、配置、直发。
   * `supervisor/messenger.py` → **`supervisor/alerts.py`**：级别、扇出、全局派发。
   * `Messenger` → **`AlertDispatcher`**；模块级 `send_alert` 保留原名。
2. **传输唯一**：`AlertDispatcher` 只调 `agents.channels.sc_send`，
   **不许再私写一份发送**（form/URL 分叉就是这样来的）。
3. **删除零调用 API**：`configure_dingtalk` / `configure_serverchan` /
   `configure_custom_webhook` / `custom_webhooks` / `send_test_message` /
   `configure_global_messenger` / `MessageLevel`。
4. **钉钉告警保持停用**：`send_alert` 原先就没有实际走钉钉（整段注释），
   本次只把事实写清楚；`agents.channels` 仍提供 `DingReminder` 直发能力。

**为什么不合并**：`agents` 是「外部通信适配」，`supervisor` 是「运维监控」。
把告警策略塞进适配层、或把协议细节塞进 supervisor，都会把两层揉在一起；
真正的病是**两份传输实现**，先收口它。

---

## 二、行为影响

* `send_alert` 现在**支持 `sctp` key**（旧实现会打 `sctapi.ftqq.com/{sctp...}.send`，
  必然 404）—— 这是修复，不是单纯重命名。
* 未配置时的提示从「未配置默认 Messenger」改为「未配置 Server酱告警渠道」。
* `supervisor` 不再 import `DingReminder`；但 `agents.channels` 顶层仍 import
  `alibabacloud_dingtalk`，所以 **惰性导入仍是独立待办**（见 `GolemQ/__init__.py`
  的注释），本次不改。

## 三、验证

* `TestAlertDispatcher`（3 条）：告警必须调 `sc_send`（钉住「不许再私写」）；
  传输返回 `{'error':…}` ⇒ `False`；无渠道 ⇒ `False` 且不发送。
* `TestScSendUrl`（3 条）：普通 key / `sctp` key 的 URL；非法 `sctp` key 抛 `ValueError`。
* 全量套件见当日 worklog。
