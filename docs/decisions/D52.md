## 一、`datetime64` 精度：ns → µs（最危险，**静默**）

**pandas 3.0 把默认 datetime 精度从纳秒改成微秒**：

```python
pd.to_datetime(...).dtype        # pandas 2.x: datetime64[ns] | pandas 3.x: datetime64[us]
series.astype(np.int64) // 10**9 # pandas 3 上直接少 1000 倍，不报错
```

本次实测症状：`reality_feat_rows` 的 doctest 给出 `1767596` 而不是 `1767596400`
（**键**写小三个数量级）。

### ⚠️ 关键结论：**一个全局标量系数不够用**

用户 2026-10-17 提议「系统固态常量，启动时按 pandas 版本赋值这个系数」。
落地时实测发现：**pandas 3 是按输入推精度的，同一次运行里几种精度并存**：

| 构造方式 | 得到的 dtype | 秒系数 |
|:--|:--|--:|
| `pd.to_datetime(date 对象)` | `datetime64[s]` | **1** |
| `pd.to_datetime(字符串)` | `datetime64[us]` | 1e6 |
| `pd.to_datetime(Series)` | `datetime64[us]` | 1e6 |
| pandas 2 的默认 | `datetime64[ns]` | 1e9 |

证据：`reality_save` 的 `day_dt` 走的正是 **`date` 对象**那条路（秒），
拿 µs 的 1e6 去除 ⇒ `date_stamp` = **`1767`**（当场红了 doctest）。
⇒ **系数必须按每条序列自己的 dtype 查**，不能按"版本"取一个标量。

### 落地

| 位置 | 内容 |
|:--|:--|
| `core/constants.py` | `EPOCH_UNIT_TO_SECONDS = {s:1, ms:1e3, us:1e6, ns:1e9}`（**固态常量**）+ `epoch_divisor(dtype)`（naive / tz-aware 都收，未知单位**响亮抛错**）+ `EPOCH_DIVISOR`（pandas 当前**默认**精度的系数，只用于诊断）|
| `markets/StockCN/kline83.py` | `epoch_seconds(series)` → `naive.astype('int64') // epoch_divisor(naive.dtype)` |
| `markets/StockCN/reality_save.py` | `date_stamp` / `time_stamp` 改调 `epoch_seconds` |
| `markets/StockCN/realtime.py` 资金流 `date_stamp` | 同样按 dtype 查系数。⚠️ **不改口径** —— 那里是 naive-as-UTC，挪成 `epoch_seconds` 会差 8 小时，是另一个决定（该函数**零调用方**，只是别留成哑雷）|

`metadata_save.day_stamp` 与 `kline83.bj_date` **不受影响** —— 它们走 Python
`datetime.timestamp()` / `.to_pydatetime()`，与 pandas 精度无关。

`analysis/pivot.py:386` **刻意不换**：那里是**纳秒域**（与 `Timestamp.value`
比 `searchsorted`，而 `Timestamp.value` 恒为 ns），换成秒会错。已在代码里注明。

### 守卫：`test_cases/test_epoch_divisor.py`（9 条）

* 系数确实等于 pandas **实际** dtype 的倒数（不是写死的数）；
* 四种单位逐个验；`date` 对象那条（`datetime64[s]`）专门钉住；
* **全树扫描**：token 流里（跳过注释与字符串）不许再出现 `// 10 ** 9` /
  `// 1000000000` / `// 1e9`。**已验它会红**（注入一处违规 ⇒ 当场 FAILED）。

## 二、`Series[整数]` 从「按位置」变「按标签」

`analysis/regtree.py:243` 的 `seq_data[i]`（`seq_data` 是 `seq_index` Series，
索引是日期）⇒ `KeyError: 0`。**改 `.iloc[i]`**。2.x 时代那只是 FutureWarning。

## 三、`float(1×1 np.matrix)` 直接抛

`analysis/regtree.py:198` 的 `float(X * model)`（`X` 是 1×n `np.matrix`）⇒
numpy 2.x：`TypeError: only 0-dimensional arrays can be converted to Python scalars`。
**改 `float((X * model).item())`** —— 取的是同一个标量，逐值不变。

## 四、日族 `datetime` 列的类型分裂（端到端实跑才暴露）

15min / 60min 的检出会**同时往日族写一笔**，那个 `datetime` 是 `Timestamp`——
pandas 2 下它被原样放进文档，以 **BSON date** 落库；而 4.4 存量与分钟族都是
**字符串**（`GQ_save_daily_metadata_reality` 用 `dt.strftime`）
⇒ **同一列两种类型**。

`reality_feat_rows` 补一条 `elif`：日族若自带 `datetime` 列，同样格式化成本字符串。
**实测证据**：迁移来的 400 行是 `str`，新写入的 2 行是 `datetime` —— 只看代码看不出来。

## 剩下的风险

* 测试覆盖不到的运行路径仍可能有 pandas 3 的问题（**链式赋值在 CoW 下会静默失效**）。
  已 grep 过一遍：命中的都是 numpy 数组 / dict，**不是** DataFrame，暂无发现。
  但这条**只能靠"跑的时候留意"**，不是一次性证明。
* `regtree.py` 仍在用 `np.matrix`（`PendingDeprecationWarning`）—— **没动**：
  换 `ndarray` 会改 `X * model` 的乘法语义（`*` 在 matrix 是矩阵乘、在 ndarray 是逐元素），
  是一次重写而不是兼容修复。
