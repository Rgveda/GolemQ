# D81. `stage` 权威源 = **4.4 搬运**；新树两条重算链全部删除

- **日期**：2026-11-16

  `analysis/reality_attach.py::_stage_before_fill`、

- **测试**：`test_cases/analysis/test_reality_attach.py::TestStageBeforeFill`、
  `test_cases/pipeline/test_review_pipeline.py`

## 背景

`stage`（GARIDENT 档位，`-0.5 / 0 / 0.5 / 1 …`）在 8.3 里先后有**两条重算链**，
两条都被用户 2026-11-16 判定为**有重大隐患**：

| 版本 | 位置 | 问题 |
|:--|:--|:--|
| v1 | `coldstart._stage_columns`（日线帧、`iloc[::21]`≈月频 checkpoint、502 **日**窗口） | 与 60min 链结果差 26%（实测 000711：`garPD→stage` 与 stage 列 545/2,089 不相同） |
| v2 | `calc_stage_frame` / `calc_stage_series`（60min 帧、21 **根** checkpoint、502 **根**窗口） | 与库里 39 根 `-0.5` 的"正确"值对不上（旧数据/旧复权下的结果不可复现；2026-01 窗口三条链都给不出 -0.5） |

根本矛盾：**同一列由两条不同粒度的 K-Means 链产出，谁也不知道该信谁**。

## 决定

1. **`stage` 从 4.4 旧库搬运**（`golemq.stock_ta_reviews`，每根 60min bar 一行，
   到 2026-11-13），新树**不再重算**。用户口径：「4.4 有值才是对的」。
2. **`GAR_P`（4.4 绝对价带）→ `garPD`（比值带）** 一并搬运：
   `garPD = GAR_P ÷ 锚日 15:00 的 4.4 close`，`garPAnchor = 锚日`。
   锚日 = `GAR_P` **发生变化**的那根 bar 的日期（带子只在 checkpoint 更新，之后 ffill）。
3. **`bstStgBf / epStgBf` 不落库**，由 `reality_attach._stage_before_fill` 现算：
   - `bstStgBf = Timeline_duration(stage < -0.00168)`；
   - `epStgBf  = Timeline_duration((garPClr < 0.927) & (DEA_ZERO_TIMING_LAG < MACD_CROSS_JX_BEFORE))`；
   - **`stage` 不覆盖**（搬运值优先）。
4. 两条重算链及其工具**删除**：`_stage_columns`、`calc_stage_frame`、
   `calc_stage_series`、`stage_family_by_day`、`tools/backfill_stage.py`、
   `tools/backfill_stage_gard.py`。`contract.STAGE_COLUMNS` 降级为
   **attach 的只读 join 名单**（不再进 `HOUR_NATIVE_COLUMNS`）。

## 验证（2026-11-16，全量）

```
[stage44] 5152 个码  ok=5152  skipped=0  error=0  rows=13,372,161  612s
[stage44] verify: match=13,890,028  mismatch=0  missing=198,613
```

- **mismatch = 0**：两边都有值的 bar，8.3 `stage` 与 4.4 `STAGE` 逐条相同；
- `missing` 是覆盖差异（4.4 首个 checkpoint 之前没有 STAGE，或行不匹配），不是不一致。

## 搬运时踩到的坑（见 `PITFALLS.md` P49）

8.3 的 reality 表里有**重复 datetime + 截断 time_stamp** 的坏行
（实测 000009：`time_stamp=1711436` vs 4.4 的 `1711436400`，同码 1,743 个重复 datetime）。

（用户 2026-11-16：「其他都不要做改动」）。
