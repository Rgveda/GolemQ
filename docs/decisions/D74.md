# D74. `se` / `ZenPivotCnt` 从 60min 契约移到日族（日频）

- **编号**：D74
- **日期**：2026-10-28
- **索引**：[DECISIONS.md](../../DECISIONS.md) —— `grep D74`，或直接开这个文件

**背景**：D71 §三 记着「day 表要不要 `se` / `ZenPivotCnt` 的日频副本」待定。
用户 2026-10-28 明确：**要 day 表日频，60min 频反而可以移除**。

## 一、口径

| 列 | 日族口径 |
|:--|:--|
| `se` | **日收盘价**的 `antropy.sample_entropy`，截至该日最后 **≤540 个交易日**（≈ 旧 60min 版 2160 根的时间跨度，4 根/日），`round(..., 3)` |
| `ZenPivotCnt` | 与旧 60min 版**同一个 60min CZSC 因果口径**，只取该日 **15:00** 的那个值；**用全历史 60min（2016 锚点）算** |

⚠️ `se` 的数值会与旧 60min 列**不同**（频率变了）：000711 2026-10-23
旧 60min `se=0.008`，新日频 `se=0.022`。这不是回归，是定义变更。

⚠️ `ZenPivotCnt` 的 **窗口口径变了**：旧 60min review 只喂 900 天，
新日族喂 **2016 起全历史**（`REVIEW_ANCHOR_DAY`）。中枢计数是**累计值**，
窗口变长计数会变大：000001 2026-10-27 旧值 **8** → 全历史 **47**。
这不是 bug，是修正（数据本来就有 1999 年起的 60min，见
[`docs/data_inventory.md`](../data_inventory.md)）。

## 二、代码改动

* 新增 `pipeline/review/steps/day_extra.py`：
  `sample_entropy_daily(day, dates)` + `pivot_counts(ohlc60, cutoffs, code)`；
  `pivot_counts` 对**帧未覆盖的时刻返回 NaN**（`causal_pivot_count` 在首根之前
  也返回 0，不能把「没数据」冒充「0 个中枢」）。
* `day_core_step` 只对 `day_target_set` 计算这两列；`_day_row` 增加两个键。
* `contract`：`DAY_COLUMNS` **28 → 30**；`HOUR_EXTRA_COLUMNS` 删除，
  `HOUR_COLUMNS` **40 → 38**。
* `pipeline._required_freqs`：请求日族时**同时取 60min**（`ZenPivotCnt` 要用）；
  60min 帧缺失时该列 NaN。`_fetch_frames` 在请求日族时把 60min 起点改为
  **`REVIEW_ANCHOR_DAY`（2016-01-01）**，不再用 900 天（D74 追加，见 §三）。
* `zen_snapshots_step` 不再算这两列；`reality_attach` 不再做 60min 精确 join，
  改随 `_attach_day` 因果映射。
* 删除死模块 `steps/hour_extra.py`（原 `hour_extra_step` / `build_hour_extra_steps`
  已被 `zen_snapshots` 合并，无调用方）。
* 新工具 `tools/backfill_day_extra.py`；删除 `tools/backfill_hour_extra.py`。

## 三、存量迁移（2026-10-28 实测）

`tools/backfill_day_extra.py`：

* `se`：按新口径**重算**全部 review 日行；
* `ZenPivotCnt`：优先从 `stock_reality_feat_60min` 每**日最后一根**复制
  （15:00 采样）；60min 列被 `$unset` / 旧行没有时，回退到**现算**
  （`get_kline_price_min` 从 **2016-01-01** 起取全历史 60min，
  `day_extra.pivot_counts`，与 review 同口径）；
* 写库复用 `save_reality_feat(..., 'day', write_nulls=False)`。

### 数据审计（纠正「4.4 没搬全」的猜测）

见 [`docs/data_inventory.md`](../data_inventory.md)。结论：

* 8.3 的 60min / 1min 行情**没有成块缺失**；4.4 `quantaxis.stock_min(type=60min)`
  多出来的行是**重复行 + 错标频率**（混入 15min 时刻），不是 8.3 少搬；
* 60min 数据本身 **1999 年起**、1min **2017-11 起**；
  33% 的根因是 review 只喂了 900 天，不是数据上限。

### 最终覆盖（全历史重算）

```
review 日行            2,935,202
se 非空                2,935,073   （缺 129 行 = 上市初期暖机，算不出）
ZenPivotCnt 非空       2,933,407   （99.94%）
ZenPivotCnt 缺失          1,795   （只有 2 只北交所 920xxx：60min 数据 2025-09 才开始）
有值的码                 1,883
```

* 60min 侧 **`$unset` 3,906,523 行**（stock；etf/index 为 0），`se`/`ZenPivotCnt`
  在 60min 集合中已不存在。
* 000711 实测：attach 的 `se`/`ZenPivotCnt` 来自 `loaded['day']`；
  2026-10-23 `se=0.022`、`ZenPivotCnt=28`（900 天窗口下是 5，全历史重算后
  变大，属口径修正）。

## 四、边界

* `ZenPivotCnt` 已覆盖 review 日行全历史（2019-10 起）；仅 2 只北交所码在
  其 60min 数据起点（2025-09）之前为空 —— **源数据没有**，不是漏跑。
* `se` 全历史可用（受上市初期暖机限制）。
* 日族依赖 60min 取数：`--strategy review --eval fast` 本来就取 60min；
  只跑日族时会多读 **2016 起**的 60min（约 1 万根/码）。
