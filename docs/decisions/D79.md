## 背景

4.4 旧树 `--strategy mainstream` 每根 60min bar 做一次**全市场横截面**的
Dempster–Shafer 判断，以仓位输出（`策略仓位控制：PosBsln 做空比 PosNegBsln`）。
用户要求移植到 8.3，并给了两个历史验证点：

1. 2025-04-07（暴跌日）**之前仓位已为 0**；
2. 2026-06-30 ~ 07-03 出现**零仓位清仓**。

旧实现：`GolemQ_old/scribe/empirical.py:507-606`
（`calc_massive_ChartsScanAI_model`）。语义：

```
bull  = QuadPreUprBf < QuadPreEpBf
bear  = QuadPreEpBf < QuadPreUprBf 且 zDLagD < 0
omega = 其余
m_bull/m_bear/m_omega = 成员占比；仓位 = m_bull；m_bear > 0.618 强制 0
```

## 决定

1. **新树按自身口径实现并自洽，不追求与 4.4 逐值一致。**
   数据（同一份 8.3 行情）、复权（qfq/hfq/bfq 三种都试过）、窗口
   （截至 bar 的 800 天 = 2,120 根）、参数（`max_bi_count=126`）均已排除，
   差异落在**缠论实现本身**（旧树 czsc 版本未知，新树固定 0.7.10）。
2. **`zDLagD` 用新版无后视镜**（用户 2026-11-01 定）：`calc_zen_dash_causal`
   用 czsc 逐 bar 增量状态（`CZSC.update`），方向只取「当下已确认的末笔」，
   再取 `calc_event_timing_lag`；旧树把方向写在笔起点 `fx_a`（后确认的信息
   回到过去）的做法**不再采用**。`calc_zen_dash_asof`（逐 bar 重建）保留为
   慢速基准；`calc_zen_dash_dummy`（旧树原样）仅用于与 4.4 对拍。
   日线值（`QuadDwnRskLagMaj`、`POWERLINE_MAJOR`、`MACD_DELTA_MAJOR`）
   **照旧树贴到当日 4 根 bar** —— 这是旧树既有的已知前视，保留并标注。
3. **输出**：**沿用旧表名** `stock_massive_reality_60min_models`
   （ETF 用 `index_massive_reality_60min_models`），字段沿用旧名
   `PosBsln / PosPad / PosNegBsln / MasPosOnhold / mberCnt / DS_*`。
   ⚠️ 这是**全系统共用的 massive 模型表**（仓位只是其中一批字段），
   **不许**按用途另起 `*_position_*` 之类的新表名 —— 那会把全系统表切碎。
   4.4 **只读**（D75），不写回；8.3 这张同名表由本管线写。
4. **入口**：`python -m GolemQ.cli --strategy mainstream --eval <scope>`
   （`--pct-of-cores` / `--offset` 复用全局旗子，不另造前缀变体）。
   ⚠️ 这里的 **`all` = `stock_list` 全市场**，不是 scopes 的「股票∪ETF∪指数」——
   仓位是**同族横截面**，ETF/指数要各自聚合。
5. **刻意删除**旧代码里不可达的 `ds_state == 2` 分支
   （`Bel_bull+Bel_bear ≤ 1`，不可能同时 > 0.5）；`DS_CONFLICT_K` 旧树恒 0，
   不再输出。

## 增补（2026-11-01）：满仓反函数与两个事件列

清仓规则是「`m_bear > 0.618` 且占优 ⇒ 0」。按对称口径构造**反函数**：

```
PosFull = (m_bull > 0.618) & (m_bull > m_bear) & (m_bull > m_omega)
```

阈值 **0.618 不调整**（用户 2026-11-01 明确）。同一张 massive 表再派生两列：

| 列 | 含义 |
|:--|:--|
| `PosFull` | 满仓信号（bool→int8） |
| `PosFullOnset` | 满仓段的**第一根**（回测取样点） |
| `PosReClear` | **清仓暴击**：清仓段与上一段间隔 ≤4 根（「清仓→短暂重开→立刻再清仓」） |

实现：`analysis/position.py::calc_position_flags`（纯派生、不重算），
由 `MainstreamPipeline.run_market` 随每次运行写入。

### 实证（2022-06 ~ 2026-10，9 次满仓信号）

| 基准 | 5日中位 | 10日中位 | 20日中位 | 20日胜率 |
|:--|--:|--:|--:|--:|
| **科创50（000688）** | +2.60% | +2.90% | **+5.78%** | 67% |
| **创业板指（399006）** | +4.41% | +2.00% | **+8.32%** | 56% |
| 沪深300（000300，仅历史对照） | +1.43% | +0.24% | +2.61% | — |

**基准选择**：用户 2026-11-01 明确「沪深300 是老登资产」，**默认基准用科创50 +
创业板指**；沪深300 只在历史对照里出现，不再作为主结论口径。

清仓暴击在成长指数上表现为**5~10 日反弹**（科创50 +1.87%、创业板 +1.60% 中位），

## 增补二：STAGE 口径修复（2026-11-01）

**现象**：8.3 的 `stage` 全库只有整数 `{0..5}`；`STAGE_MODE`（横截面众数）
恒为 `{0,1,2}`，复现不出 4.4 的 `-0.5`（4.4 实测 `STAGE_MOD`：-0.5×754、
2.5×24、0.5×1）。

**根因（两处叠加，都是移植缺陷）**：

1. **移植源选错**：新树 `analysis/stages.py` 搬自老树**死文件**
   `GolemQ_old/analysis/stages.py`（全树无 import），而真正被调用的是
   `fractal/vXII.py::calc_garident_prices`。两者内层函数逐字相同，但**尾部顺序
   相反**：死文件「先逐 bar 判价、后 ffill 带子」；vXII「先 ffill 带子、再逐 bar
   判价」。按死文件写 ⇒ 非 checkpoint 行判价时带子是 NaN ⇒ 只有 checkpoint
   有 stage。当年那次「机械化 diff」只对了内层函数，没对外层顺序 —— 漏点在此。
2. **最后一根被强行 append 成 checkpoint**（`_stage_columns`）：用「含当根
   close 的窗口」定带 ⇒ 当日收盘永远落在某带内 ⇒ **必然整数**。老树的
   checkpoint 由 `CLT_GRP_CHK` 信号决定，目标 bar 多不在网格上，其 stage 来自
   **上一 checkpoint 的带子** —— `-0.5` / 半档正是这么来的。

**修复**：

* `stages.py`：`GARIDENT_PRICE.ffill()` 移到逐 bar 判价**之前**（与 vXII 一致）；
* `coldstart._stage_columns`：**不再**把最后一根追加成 checkpoint；
* 新增 `coldstart.calc_stage_series(ohlc)`：**全帧一次算**，`native_by_day`
  与 `tools/backfill_stage.py` 共用（避免「增量」与「回填」两套口径）；
* `tools/backfill_stage.py`：重算 `*_reality_feat_60min.stage`（当日 4 根共用
  15:00 的值，只改已有行）。

**验证**：600519 全序列（2016 起、10,481 根）修复后 stage 出现
`-0.5×258`、半档 `×1,375`；修复前全为整数。

**保留的近似（已知差异）**：checkpoint 网格仍是 `iloc[::21]`，老树用
`CLT_GRP_CHK > 0`（compact 特征信号，新树尚无该 producer）。要做到逐值一致，
需补齐该信号链；当前按 21 根近似，并在文档标注。

## 增补三：「空仓 + STAGE_MODE=-0.5」底部过滤器（2026-11-01）

**定义**（用户 2026-11-01）：

```
PosBottom = (MasPosOnhold <= 0) & (STAGE_MODE <= -0.5)
PosProbe  = PosBottom ? m_bull : MasPosOnhold   # 底部时撤销强制清零，回到原始 m_bull
```

`STAGE_MODE` = 当日（15:00）横截面 `stage` 的**众数**（旧树 `MAS.STAGE_MODE`），
由 `MainstreamPipeline.stage_mode_by_day()` 从 review 表聚合（Mongo `$group`
先数频次，再本地取众数）。

**落库**：`stock_massive_reality_60min_models` 增三列
`STAGE_MODE / PosBottom / PosProbe`（`save_position_series` 自动带上）。

**实证（9 次触发，2023-10-23 ~ 2026-06-26）**：

| 持有期 | 科创50（见底组 vs 空仓基准） | 创业板指（见底组 vs 空仓基准） |
|--:|:--|:--|
| 5 日 | +2.55% vs -0.32% | +2.98% vs -0.43% |
| 10 日 | +4.80% vs -0.69% | +4.89% vs -1.06% |
| 20 日 | +8.26% vs -0.20% | +10.31% vs -1.32% |

触发日：2023-10-23、2024-01-22/23、2024-02-01/02/05/06（雪球底）、

## 增补四：雪球底识别 `PosDeepBottom`（2026-11-01）

用户 2026-11-01：2024-02-05（雪球底）此前只有「`STAGE_MODE<-1e-12`」一个条件，
锁不住。实测 10 个 -0.5 日子后提出复合条件：

```
PosDeepBottom = (STAGE_MODE < -1e-12)
              & (连续 ≥3 个交易日 STAGE_MODE < -1e-12)
              & (m_bear >= 0.90)
```

**全序列（4,245 根，2022-06 ~ 2026-10）唯一命中**：2024-02-05 15:00 与
2024-02-06（4 根）——正是雪球底。旁证：

* 只有 2024-01-31~02-06 这一段 `-0.5` 是**多日连续**（其余 6 次全是单日）；
* 02-05/06 的 `m_bear` 达 **0.908 / 0.946**（几乎全市场看空）；
* 2026-06-26 的假底：过去 20 日 **+21%**（上涨途中回踩），再加
  「科创50 20 日收益 < 0」即可排除（放宽版已唯一命中，此条作冗余保险）。

**落库**：`stock_massive_reality_60min_models` 增
`StageModeStreak`（连续交易日 -0.5 计数）与 `PosDeepBottom` 两列。

⚠️ 样本只有 1 次事件（5 根 bar），属于「事后唯一性」而非统计显著；
后续新底部出现时需继续观察。

## 增补七：Massive 快照聚合改为「注册表 + 一次 groupby」（2026-11-02）

用户否掉了「每加一列就写一个方法、每次全表扫一遍」的做法。旧树
`analysis/chip_dist.py::calc_massive_snapshot_chip_dist` 就是**一次
`groupby(level=[0]).apply(...)`** 产出 20+ 个 MED/MODE/COMBO 契约列。

新结构 `pipeline/mainstream/snapshot.py`：

* `Agg(target, source, kind, pre, drop_zero)` 一行一个契约；
* `SNAPSHOT_AGS` 注册表 —— 加契约 = 加一行，不改循环；
* `snapshot_frame()` 一次 `groupby(ts).apply(aggregate_snapshot)`；
* `MainstreamPipeline.snapshot_contracts()` 负责装载源列 + 逐码虚拟列
  （`m9tCmpod = calc_m9t_combo(m9t, m9tLagMajR, m9tLagWekR)`），再调上表。

当前落库的 7 列：`STAGE_MODE`、`POLYNOMIAL9_NORM_MAJOR_MEDIAN`、
`RETURN_COST5/95_MEDIAN`、
`MAGIC_NINE_TURNS_DUMMY_COMPOUNDED_MODE`、`M9T_LAG_CMB_MED`、
`MAGIC_NINE_TURNS_TIMING_LAG_COMPOUNDED`（最后这列 = 市场级 COMBO 再取
event-lag，旧树 `chip_dist.py:1380`）。

⚠️ `FBP_CLR_NORM(_MAJOR)_MEDIAN` **已移除**（用户 2026-11-02：`prophetClrNorm`
