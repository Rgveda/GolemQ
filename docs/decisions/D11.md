# D11. `--save tdx`：K 线直写 8.3 + **增量按水位**，参考数据**不强制 pytdx**

- **编号**：D11
- **日期**：
- **索引**：[DECISIONS.md](../../DECISIONS.md) —— `grep D11 DECISIONS.md`，或直接开这个文件

> ⚠️ **取值部分已被 D14 取代（2026-10-09）**：`x` / `all` 已删除，只收
> `tdx` / `pytdx` / `qmt`。下面这条决定的其余内容（增量口径、拒绝的方案）仍成立。

**决定**（2026-10-08）：新增 `python -m GolemQ.cli --save tdx`（≡ 老树 `--save x`，
取值收 `tdx` / `x` / `all`），把老树 `save_x_func()` 的覆盖面搬到新树，**只写 8.3**：
参考数据 + stock/index/etf 的 day 与 1/5/15/30/60min + `stock_xdxr`（含 `stock_adj` 重算）。
首次按**增量**：逐 code 取该集合里 `ts` 最大的那根，**再往前 `margin_days`(5) 个交易日**
作为窗口起点，窗口整体「先删后插」。

**拒绝的方案 A：参考数据也强制走 pytdx。** pytdx 枚举不到北交所（实收 5,226 vs
`stock_list` 的 5,574），而 `save_refdata` 对 `stock_list` 带 `delete_delta_key` →
**会删掉现有 348 只北交所**；且 pytdx 至今不支持 `etf_list`。故参考数据沿用
**默认源优先级**（= 今天的 `--save-x`），只有 K 线强制 pytdx（它本来就只有一个源）。

**拒绝的方案 B：像老树那样从 2015 全量重灌。** 8.3 已有全量数据（`stock_day`
17.9M 行、`stock_1min` 21.3 亿行），重灌的代价与风险都不必要；增量 + 覆盖核对更省。

**窗口余量 `margin_days`：默认 0**（2026-10-08 更正 —— 起初默认 5，**是我定错了**）。
水位是 **per-code** 的（每个 code 从自己最后一根起算），所以「上次跑挂在中途」天然兜住；
「收盘后把当日那根写全」也只需窗口从**水位当天**起算。实测（200 只票、日线）：
`margin=5` 每票写/删 **6.0** 行，`margin=0` 每票 **1.0** 行 —— 5,574 只票每天少写少删
约 **2.8 万行**。`margin>0` 只用于「源端回补了更早历史」的**修补**，用
`--save-margin-days N` 显式开。

**领域约定（项目所有者 2026-10-08 明确，见 `PITFALLS.md` P20）**：盘中 **`day` 不更新**
（仍是昨天那根），**盘中行情由 REALTIME 的 L1 tick 合成** —— 那是另一条路径，
与 `--save tdx` 无关。⚠️ 但 pytdx 的 day 接口**盘中会返回「当日累计」bar**，
所以盘中跑本命令会把未收盘的当日 bar 写进去 → 收盘后再跑一次即被覆盖；命令会**打印告警**。

**为什么 `index_*min` 按 pytdx 原值写**：实测存量那批与 pytdx **不同源**
（vol 比值 14–18 非常数、close 精度也不同），口径无法反推。原值照写的代价是边界处
标度跳变 —— 这是**已知并接受**的，系数收在 `kline_doc.INDEX_MIN_VOL_SCALE` 一处，
将来确认权威口径只改那一行。

**弃案 C：只补增量、不查覆盖。** 增量的水位逻辑**看不见水位之前的历史空洞**
（实测 `etf_day` 1,689 只里 739 只有缺日、`stock_adj` 138 只落后于日线）。
故同批做了 `--save-coverage` 只读报告 —— 但注意它**只证明日期存在，不证明根数正确**，
且无成交日的"洞"是**正常**的（源端就没有 bar），要逐个 triage，**不要盲目回补**。
