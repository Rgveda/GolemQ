# D88. review 单码超时的根因与三处修正

- **编号**：D88
- **日期**：2026-11-22
- **代码**：`pipeline/review/pipeline.py`、`pipeline/review/contract.py`、
  `analysis/zen.py`、`pipeline/review/steps/hour_extra.py`
- **测试**：`test_cases/pipeline/test_persist_check_columns.py`

## 现象

`--strategy review --eval etc_2` 跑 2,001 个码：
成功 1,896、**timeout 104**、no_data 1；中位 **4.8s/码**、均值 378.9s/码，
Slowest 1%（21 个码）吃掉 **19.9%** 的计算量。

用户判断：「长度不足应该很快报错，而不是 timeout」。

## 根因：**不是长度不足，是首次全量回填**

`_targets` 只返回**库里还缺**的目标。实测（`missing_targets` 直查）：

| code | 缺 day | 缺 60min | 缺 15min | 结果 |
|:--|--:|--:|--:|:--|
| 601595 | 1,700 | 1,400 | 8,145 | timeout |
| 603897 | 1,700 | 1,371 | 8,135 | timeout |
| 301159 | 1,180 | 1,452 | 8,433 | timeout |
| 688595 | 1,488 | 1,396 | 8,145 | timeout |
| 600519 | **0** | **0** | 14 | 秒级 |
| 000711 | **0** | **0** | 8 | 秒级 |

超时的码 **60min 源数据都是完整的**（601595 有 9,804 根 60min bar），
缺的是「review 从来没跑过」—— 它们要一次性回填 800 天 × 三族。

### 实测成本结构（601595，取近 20 天目标）

```
day_core        59.6s / 15 个日目标 = 3.97s/天
  ├─ chip_cost_by_day      2.3s/天  (58%)   逐日 960 根窗口跑 ChipDist
  ├─ _frame_features       1.05s/天 (26%)   M9T/Poly9/zen/RegTree(0.9s)
  └─ _coldstart_row        0.66s/天 (17%)   Prophet 全样本拟合
zen_snapshots   69.7s / 60 个 60min 目标 = 1.16s/目标
  └─ build_hour_extra_frame 44s（native_by_day 32s + stage 5.3 + chip 3.1）
  └─ 每目标 minor_features 0.30s（15min 2160 根窗口 CZSC ×3 + pivot）
```

外推一个全新码：day 1,700×3.97 ≈ **1.9h** + zen 2,037×1.0 ≈ **35min** ≈ **2.5 小时**，
超过当时的 2 小时护栏 ⇒ 判 timeout。原注释「全量回填约 36–40 分钟」是
ChipDist 逐日窗口 / HOUR_NATIVE 10 列加入**之前**的数，已过时。

## 三处修正

### ① 完成判据排除「外部工具写的列」（真 bug）

`persistence.persisted_keys` 用「契约里任意一列非空」判已持久化。
D87 补的 3,752,516 行**只有 `4QPwrlnWek`** ⇒ 被当成「已算完」，
**回填到 2024 年以前时那些 bar 会被静默跳过**。（当前 800 天窗口从
2024-09-13 起，合成行止于 2024-07-31，尚未踩到。）

改法：`contract.PERSIST_EXCLUDE = {'60min': HOUR_WEEKLY_COLUMNS}` +
`persist_check_columns(family)`；`_targets` 传它给 `missing_targets(columns=…)`。

### ② `RawBar` 构造向量化（`analysis/zen.py::raw_bars`）

`_bars_of` / `pivot_stats` / `pivot_lag_minor_window` 三处各自 `iterrows()` 逐行
建 `RawBar`。一次 2,160 根窗口的 `iterrows` ≈ **0.15s**，而一次全量回填要调
2,000+ 次。现统一走 `raw_bars()`（`itertuples` 级取值的 numpy 版本），
`minor_features` 实测 **0.30s → 0.19s（-37%）**，`zen_snapshots` 69.7s → 59.4s。

⚠️ `vol/amount` 在 `raw_bars` 里 NaN 归 0（czsc 只用价格定笔，这两个是元数据）。

### ③ 单码护栏：2h → 3h → **1.5h**（随优化重估）

最初 2h 会把正常的全量回填判成 timeout，先抬到 3h；**⑤⑥ 优化之后**成本从
~2.5 小时降到 **~45~48 分钟**（day_core 22min + zen_snapshots 23min），
护栏随之下调到 **90 分钟**（用户 2026-11-22 定），留约 2 倍余量。
超过 90 分钟基本可判定是卡住而非慢；且 ④ 的按年切块保证最多丢一块。


### ④ 按年切块、块末落库（用户 2026-11-22 方案）

即便把护栏抬到 3h，仍有码跑不完。用户提的方案：**单次 `--review` 最多只跑一年，
超过一年就每年中断一次、落库再继续**，「架构不要大改变」。

实现：`pipeline/review/pipeline.py`

```python
def chunk_targets(targets_by_family, max_years=1.0):   # 生成器
    ...   # 按**日历年**切；不跨年 ⇒ 只产出一块（老行为）
```

`run_code` 改成 `for chunk in chunk_targets(full, self.options.max_years)`：
每块设 `ctx.targets = chunk`、清空 `ctx.outputs`、跑 step、**立刻 `_write_family`**。
`ReviewOptions.max_years` 默认 **1.0**（`0` = 退回不切块）。

**为什么是 yield 而不是 `itertools.batched`**

| | `chunk_targets`（生成器） | `itertools.batched` |
|:--|:--|:--|
| 切分依据 | **日历年**（每年 250 / 4,000 个目标，不等长） | 固定个数 |
| 三族一致性 | 每块内 60min 与 15min 落在**同一时间窗** | 按个数切会把 60min 目标和它的 15min 依赖拆开（`_hour_targets` 依赖同块） |
| 中断语义 | 天然「算一块→落库→再要下一块」 | 需要自己包一层才能懒执行 |
| 续跑 | `_targets` 只返回缺口，天然续 | 同左 |

⇒ **按时间切必须用生成器**；`batched` 只在「固定 N 条一批」时才有意义，
这里三族密度差 4 倍（day 1 / 60min 4 / 15min 16），按个数切会破坏依赖关系。

**正确性验证**（601595，跨 2024-12-20 ~ 2025-01-10，day 15 / 60min 60 / 15min 240 目标）：

切块 vs 一次性，逐列逐行对比：**day 19 列、60min 76 列、15min 20 列全部一致**。
（首轮 `stage` 报过 1 行差异，复跑即消失 —— 那是 `calc_garident_price` 的 KMeans
`random_state=None` 造成的**进程间**随机性，与切块无关，见 `analysis/stages.py` 注释。）

用例：`test_cases/pipeline/test_chunk_targets.py` 8 条。


### ⑤ ChipDist：JIT 是开着的，但被**超额内存**和 **dict 往返**吃掉

核查结论：`_calcu_sin_jit` / `_calculate_chip_distribution_jit` /
`_cost_calculation_jit` / `_winner_calculation_jit` 都是 `@jit(nopython)`，**全程在用**。
慢在两头：

1. **`max_chips` 阈值表严重过供**：`price_range<=51.2`（绝大多数股票）一律给
   **50,000 档**。601595 实测只需 **3,683 档** —— 953 天 × 50,000 × 8B ≈ **762MB
   分配/次**，光内存就把 JIT 核拖到 3.07s（真实需要 ~0.08s）。
   改为 `price_range/minD × 1.25 + 500`（下限 1000、上限 500,000）。
2. **numpy → dict → numpy 往返**：`_calculate_chip_distribution` 把 (953×3,683)
   摊成 Python dict（≈3.5M 次插入，0.5s），`cost()` 再翻回数组、**且 4 个分位
   各翻一遍**（1.08s），`winner()` 又翻一遍（0.26s）。

改法：`calcuChip` 保留 JIT 的 2-D 数组（NaN 尾部填充），`ChipList`/`Chip` 改成
**惰性 property**（外部真正读到才建 dict）；`cost()`/`winner()` 命中 `self._arr`
就直接走 `_cost_calculation_jit` / `_winner_calculation_jit`。

实测（601595，960 根窗口，稳态）：

| 项 | 优化前 | 优化后 |
|:--|--:|--:|
| JIT 核（含 762MB 分配） | 3.07s | **0.08s** |
| `calcuChip`（含建 dict） | 0.55s | **0.10s** |
| `winner` | 0.26s | **0.009s** |
| `cost` × 4 | 1.08s | **0.13s** |
| **`chip_cost_by_day` 端到端** | **2.14s/天** | **0.27s/天（-87%）** |

数值：`cost(5/15/85/95)` 与 `winner` 对老 dict 路径**最大差 0.000e+00**。

### ⑥ RegTree：jit 内核**写了但没接上**（review 走的是 np.matrix 纯 Python）

`regtree_jit.py` 里 `choose_best_split` / `_ols_err` / `_ols_ws` 都是 njit，
但 review 的日族走 `calc_regtree_fractal_vXIs` → **`predict_regression_tree_branch(np.asmatrix(price))`**，
即纯 Python 递归建树（profile 里 40 万次 `np.matrix.__getitem__`）。

改法：新增 `_build_tree()`，**优先** `predict_regression_tree_branch_jit`
（ndarray、float64 连续），异常回落老的 matrix 版。

实测（450 根窗口）：纯 Python **0.81s/次** → jit 稳态 **0.007s/次**（首次含编译 1.5s）。
端到端 `_frame_features` 0.93s/天 → **0.13s/天**；5 列
（`regtreePrice/regtreeTrd/regtreeLag/regtreeSlp/rTrePrcD`）与老路径**逐值相同**。

### ⑦ 旧实现的**不可过滤**提醒（用户 2026-11-22）

`regtree_jit.py` / `ChipDistribution_jit.py` 里保留着逐行照抄老树的旧实现
（`predict_regression_tree_branch`、`_calcu_cost`、`_calcu_winner1/2`、
`tree_forecast_jit`），比 jit 快路径慢**两个数量级**。用户要求「直接删也不好，
加不能清除的强制警告，以防误用」。

实现：`core/presentation.py::legacy_python_warning(name, faster)`

* **直接写 `sys.stderr`**，不走 `warnings` —— `warnings.warn` 会被调用方 /
  测试 / `-W ignore` 用 `simplefilter('ignore')` **静默掉**，那这条提醒就没用了；
* 同一进程内**每个名字只报一次**，回填时不会刷屏；
* 生产路径（`_build_tree` 的 jit 分支、`cost()`/`winner()` 的数组直算）**不触发**。

被挂上提醒的地方：

| 旧实现 | 提示改用 |
|:--|:--|
| `regtree.predict_regression_tree_branch` | `predict_regression_tree_branch_jit` |
| `regtree.tree_forecast_jit`（名字带 jit，实为纯 Python 遍历） | —— |
| `ChipDistribution._calcu_cost` / `_calcu_winner1` / `_calcu_winner2` | `cost()` / `winner()` 的数组直算 |

用例：`test_cases/analysis/test_legacy_warning.py` 5 条（写到 stderr / 只报一次 /
`simplefilter('ignore')` 压不住 / 两个真实旧函数确实报警 / 生产路径不报警）。


### ⑧ 消掉 numba 的 `NumbaPerformanceWarning`（2026-11-22）

review 跑起来会刷：

```
regtree_jit.py:924: NumbaPerformanceWarning: '@' is faster on contiguous arrays,
  called on (Array(float64, 2, 'C', ...), Array(float64, 1, 'A', ...))
  Xty = dt @ y
```

原因：`_ols_err` / `_ols_ws` 里的 `dt @ y`，`dt` 是 C 连续、`y` 从切片传进来
常是 **A 布局**（非连续）。numba 会给慢路径并告警。

修法：两个核的入口各加一行 `y = np.ascontiguousarray(y)`。既消掉告警，
也让 matmul 走快路径。**数值不变**（拷一份连续内存，语义等价）。

验证：`warnings.simplefilter('error', NumbaPerformanceWarning)` 下跑
`_frame_features` 全程不再抛；RegTree 5 列仍与旧路径一致。



### ⑨ worker 崩溃的真正根因是**内存**，不是批次（2026-11-22 更正）

用户 1,742/2,001 时 loky 报 `A worker stopped while some jobs were given to the
executor`，随即整轮降级成串行，并冒出 `[legacy] regtree.predict_regression_tree_branch`。

⚠️ **我第一版改错了方向**（把 codelist 切成 256 一批并行）—— 用户当场否掉：
**「不得改批次，tqdm 必须逐 code，这点没得商量」**。批次已撤回。

**真根因（用户点出）**：`ChipDistribution_jit` 的 numpy 超额分配。

| 码 | 修复前 max_chips | 数组内存（两个 float64） |
|:--|--:|--:|
| 601595 | 50,000（阈值表） | 381MB × 2 |
| **688502**（价格区间 622.9） | 按需 = 78,364 档 | **1.13GB × 2**，加 padding 拷贝峰值 ~4GB |

36 个 worker 里只要撞上几个这种码就把机器内存打满 ⇒ worker 被杀；
串行重跑落在父进程、numba 首次编译同样失败 ⇒ RegTree 回落纯 Python。
**整条链是「内存 → worker 死 → 降级 → 纯 Python」**，与批次无关。

修法（`ChipDistribution_jit.py`）：
* `max_chips` 按 `price_range/minD × 2 + 128` 定容（2 倍是因为每天网格起点
  不同，并集实测会超 12%），并以 **256MB/次** 的内存预算封顶；
* 超预算时**放大 minD**（分箱变粗）而不是截断价格轴；
* JIT 内部加硬保护：并集仍超容量就截尾，**绝不抛异常炸 worker**；
* 去掉 padding 的三份大拷贝（`np.where`）→ 原地写 NaN。

效果：最坏 688502 从 **1.13GB×2 → 134MB×2**；601595 57MB×2。36 个 worker 同时跑也安全。

**保留的降级路径**（与批次无关）：`run_codes` 仍是一份 codelist、一个 `Parallel`、
`tqdm` 的 iterable 就是完整码表、`batch_size=1`（保证进度逐码）；真遇到 worker
被杀时**原样并行重试一次**（已完成的码行已落库，`_targets` 只返回缺口），
仍失败才退串行兜底，并且两次都打 `[WARN]`。

诊断增强：`[regtree] code=XXXXXX jit 建树失败，回落纯 Python：<异常>`、
`[legacy] … （code=XXXXXX）` —— 下次能直接定位到码。

### ⑪ `LinAlgError` 才是 `[legacy]` 刷屏的元凶（2026-11-23 定位）

用户 2026-11-22 的 review 日志里：

```
[regtree] code=603983 jit 建树失败，回落纯 Python（慢约 100 倍）：
          LinAlgError: Array must not contain infs or NaNs.
[legacy] regtree.predict_regression_tree_branch …（code=603983）
```

根因：`calc_regtree_fractal_vXIs` 的建树输入 `price = [bar 序号, HMA10]`，
`HMA10` 在**窗口头部 / 停牌段**会是 NaN；numba 的 OLS（`np.linalg.solve`/`det`）
遇到 NaN 直接抛 `LinAlgError` ⇒ `_build_tree` 回落到**慢 100 倍**的纯 Python 建树。
几个次新码（603983 / 605198 / 605287 / 605289 / 605296）因此每码都付这个代价。

⚠️ **第一次我只改了 `calc_regtree_fractal_func` 与 `_vXI`，等于没改** ——
review 的日族与 60min 原生列走的是 **`_vXIs`**。三个入口必须同时改，
且 `_build_tree` 里再加一层兜底（`xgboost/markup.py` 也走 `_func`）。

修法：
* `_func` / `_vXI` / `_vXIs`：`price` 按 `np.isfinite(...).all(axis=1)` 过滤，
  `ohlc_data` 同步 `loc` 收窄（保证 `price[:,0]` 与行一一对应）；
* `_build_tree`：入口再兜一次（过滤后不足 3 行才报错）。

用例：`test_regtree_builder.py::TestNanDoesNotFallBack` 2 条
（HMA10 打洞 ⇒ 不出现 `[legacy]`/`[regtree]` 且仍产出 regtreePrice；
`_build_tree` 单点 NaN 自行过滤）。

### ⑬ 清理「新旧并存」的重复实现（用户 2026-11-23 总原则）
