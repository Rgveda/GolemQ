# D21. `--save tdx` 跑到 76% 卡死 —— **两个真因**，都不是业务逻辑

- **编号**：D21
- **日期**：
- **索引**：[DECISIONS.md](../../DECISIONS.md) —— `grep D21 DECISIONS.md`，或直接开这个文件

**症状**（用户 2026-10-09 实报）：banner 上参考数据全绿、K线前五个频率全绿，
`60min` 卡在 `603527: 76%|...|4239/5579 [12:51<6:26:59, **17.33s/code**]`，
"运行很久以后卡住"。

### 真因 ①：BLAS 守卫**没从老树搬过来**（新树重构时漏的）

老树 `GolemQ_old/__init__.py` 顶部有一段必须在 **numpy 首次 import 之前**执行的
`setdefault` 循环，把 `OPENBLAS/OMP/NUMBA/MKL/NUMEXPR/VECLIB` 线程数压到 1。
**新树没有它**（全树 grep 零命中）。

numpy 的 OpenBLAS **按线程**预留提交量。本机 **18 核** 实测：

| 条件 | 单进程提交量 |
|:--|--:|
| 无守卫（直接 `import numpy`）| **6573.9 MB** |
| 设线程=1 | **19.8 MB** |

`jobs=4`（1 主 + 4 worker）折合 **32.1 GB → 0.43 GB**。撞的是 Windows 的
**commit limit**（物理内存 + 页面文件，**不是**物理内存），所以症状是
**"越跑越慢、迟迟不结束"而不是报错**。

已按老树原样搬回（`setdefault` 语义：调用方自己 export 的不覆盖），
并加了**回归测试** `test_cases/test_blas_guard.py` —— 其中一条**起干净解释器**
验真行为（在本进程里断不出来，变量可能早被父进程设过）。

### 真因 ②：`DEFAULT_HOSTS` 第一台是**死服**，而 `new_api()` 每次都从表头重试

2026-10-09 逐台实测 `connect + get_security_count(0)`：

| 服务器 | 探针 |
|:--|:--|
| **`123.125.108.14`**（原列表第一位）| **超时 10.055s** ✗ |
| `115.238.90.165` | 0.127s ✓ |
| `180.153.18.170` | 0.153s ✓ |
| `shtdx.gtjas.com` | 0.182s ✓ |

它 **TCP 连得上、协议层不应答**（所以纯 socket 连通性测试查不出来 —— 我第一轮
就是这么误判的）。`new_api()` 每次从表头试 → **每次建连白等 10s**。
一次 `--save tdx` 有 5,579 code × 6 频率 = **33,474** 次 `new_api()`。

**两处修**：
1. `new_api()` **记住上次成功的那台**、下次优先试它（`self._host` 原本只当排障信息）；
2. `DEFAULT_HOSTS` 把那台**降到最后**（不删 —— 这类服会时好时坏，真回来了会自动被选中）。

实测：`new_api()` **20.040s → 0.150s**（133×），33,474 次折合
**2795 分钟 → 20.9 分钟**。这才是 `17.33s/code` 的真身。

⚠️ **教训**：`connect(time_out=10)` 对**后续调用**也生效（pytdx 拿它设 socket 超时），
所以探针超时也是 10s —— 「TCP 通」与「协议层应答」是两件事，排障时要分开测。
