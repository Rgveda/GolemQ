## 二、持久化检查（`pipeline/review/persistence.py`）

### 判据：**看表，不看水位**

`persisted_keys(code, family, market_type, db, columns, min_columns)`：

1. 从目标 `*_reality_feat_*` **只投影** `columns`（默认该族契约全部列）；
   ⚠️ **用户 2026-10-20 定：判据用「任一契约列」** —— 因为后期还会增加落库列数，
   新增列会自动进入 `FAMILY_COLUMNS`、自动参与巡查，不需要改这里。
2. 一行里**至少 `min_columns` 列非空** ⇒ 该时间键算「已持久化」；
   默认 `min_columns=1`（即「任一契约列」）。传更严格的列/阈值可以要求
   例如 `zDLagR` 与 `zDLagMinR` 都在（参数化，不写死）。
3. **CV-only 行不算**（4.4 迁移来的 `ClsMaj` 等 review 列全空）—— 它们必须被补算；
4. `missing_targets(...)` = 源帧时间 − 已持久化键；`force` / `from_date` /
   `recheck_days` 是显式覆盖。

为什么不用 `pipeline_watermarks` 做判据：水位是侧表，手工删行、迁移、别的写口都会
让它与表内容分叉；表内容才是唯一事实。水位只保留 `status/error` 观测，不参与选行。

### 最少计算/写入多少 bar

* **目标下界**（`TARGET_LOOKBACK_DAYS`）：day `2560` 天、60/15min `800` 天
  —— 与老树 `last_day-2560d` / 默认 800 天一致。更早的源数据只用于**暖机**，
  不产生新行。
* **暖机**由各 step 自己切：日 1008 / 周 2160 / 60·15min 2016 / regtree 450；
  目标只影响“写哪些行”，不改输入窗口。
* **整行 NaN 不写**：`_write_family` 在落库前丢掉契约列全空的行 ——
  否则持久化检查会把它们误判成「已持久化」而永远不再补算。
* **不重复写**：`missing_targets` 已排除表里已有的键；写入仍是幂等 `$set`。

## 三、验证

* `TestPersistence`：构造「一行有 review 列、一行只有 CV/空」的假表，
  断言只补后者；`min_columns=2` 时一行只有 1 列非空也算缺失。
* 显式覆盖各有用例：`force=True` 忽略已持久化集合；`from_date` 是**严格下界**
  （当天不算）；`recheck_days` 只把窗口内已持久化的行重新纳入、窗口外不重算；
  空源帧返回空。
* `TestDbInjection`：写口/水位必须用调用方传入的 DB 实例。
* 真实运行：600519 已有 2026-09-08…10 的 review 行，`--review-from 2026-09-01`
  只补 09-02…07 中缺失的日期，已存在的三天不重算。

## 四、已确认（2026-10-20）

1. **巡查列 = 任一契约列**（`min_columns=1`）：后期增加落库列数时自动纳入，
   不改判据；更严格的检查用参数传 `columns/min_columns`。
2. `fill_turnover` / `merge_metadata_into_feat` / `save_moneyflow` /
   `migrate_reality_feat_from44` **全部改为调用 `save_reality_feat`**：
   保留“只覆盖自己列”的语义（只把本模块 payload 交给写口），入口唯一。
