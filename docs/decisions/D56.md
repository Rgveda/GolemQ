## 二、决定（用户 2026-10-20）

1. **ETF 拆分：关闭** —— 数据早已完成，`index_*` 零 ETF，无数据丢失。
2. **两处路由变更：不搬数据** —— 查库确认两侧都为空，分类修正即可。

---

## 三、为什么不搬

* **无消费方**：两组代码不在任何现行名单里，universe 构建不会选中它们；
  它们是分级基金/LOF，已退市或终止。
* **成本与风险不成比例**：合计 **1.596 亿行**（约 160M），其中 1min 占 1.149 亿。
  时序集合不支持 upsert，搬迁需 `$merge`/`insert_many` + 删源 + 可逆台账 +
  抽样核对；操作窗口长，出错代价高。
* **读空是静默的，但只影响这些无消费方的历史代码** —— 这一点必须记录，
  避免将来有人误以为「路由对了、数据自然在」。

---

## 四、将来什么情况下再搬

若某个策略/回测**确实需要**分级基金或 LOF 的历史行情：

1. 先确认所需代码与频率（通常只需 day/60min/15min，可省掉 1min 的 1.149 亿行）；
2. 按可逆方案搬：**先写目标、后删源**（中途失败只会重复；反向会丢数据），
   目标建 `(code, ts)` 唯一索引，重跑幂等；
3. 记一份「搬了哪些 code / 频率 / 行数」的台账，抽样逐值核对；
4. 搬完用 `market_prefix` 的读路径回读抽样，确认非空且值一致。

**不要**为了让数据可达去改分类器：`150xxx` 是分级子份额，不是 ETF
（官方号段见 `PITFALLS.md` P12）；**也不要**把 `FUND_CN` 的路由从 `index_*`
改到 `fund_*` —— 那是 D/E 的既定选择，本次不推翻。

## 五、可复用的核对方法

全程只读，未写任何集合：

1. 每集合 `distinct('code')`（`code` 是索引首列，比全表扫快得多）；
2. 对每个 code 跑 `is_stock_cn(code)[1]` 分类，与目标集合对比；
3. `etf_list` ⟷ 分类器**双向**比对（`etf_list - 分类ETF` 与 `分类ETF - etf_list` 分别定性）；
4. `index_*_removed` 的 code 集合与 `etf_*` code 集合求差，确认搬迁无丢失；
5. 残留代码在 `stock_list` / `etf_list` / `index_list` 中的成员检查（均为 0）。
