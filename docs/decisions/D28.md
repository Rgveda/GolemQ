# D28. 收盘后的**快路径**：整段跳过（连逐只读都省）—— 双因子（2FA）判定

- **编号**：D28
- **日期**：
- **索引**：[DECISIONS.md](../../DECISIONS.md) —— `grep D28 DECISIONS.md`，或直接开这个文件

**用户 2026-10-09 定**（原话：「收盘后…检查是否当天K线已经存储完毕…那么就不再做任何
tdx 服务器连接，直接 continue」「类似于 2FA」「这样就不用考虑是否还在5小时TTL之内了」）。

**判据（三条，见 `kline_save.fast_skip_reason`）**：

| # | 因子 | 查什么 |
|:--|:--|:--|
| ① | 时序 | **不是**「盘中 × 分钟」—— ⚠️ 承重，见下 |
| ② | **记账** | 签到表里该集合的时间戳落在「**最近一次收盘之后**」 |
| ③ | **数据** | 集合里真有 ``ts >= 最近一次收盘那一批的最早那根``（探针，~50ms）|

**②+③ 就是用户说的双因子（2FA）**：两个**互相独立**的来源 —— 记账是**运行留下的记录**，
数据是**数据本身**。记账被误删/漏记 ⇒ ③ 仍会拦（库里查不到那批）；数据被误删 ⇒ ③ 直接拦。
**AND，不是 OR**。任一条不过 ⇒ 走常规路径（探针 + 逐只水位）。

**为什么它成立**：记账**只在「全宇宙的跑法」里发生**（`codes is None`，2026-10-09 加的规则）
⇒ 「上次全查在收盘之后」**等价于**「**每一只 code 都在那次全查里被处理过**」。

**为什么①承重**：盘中「最近一次收盘」是**昨天** 15:00。不加①的话，周一 10:00 会认为
「周五收盘之后扫过了 ⇒ 已覆盖」⇒ **跳过周一的分钟线**（那是真丢数据）。
`day` 不受影响 —— 盘中本来就不写当天日线，跳是对的（这正是盘中 `stock_day` 秒过的原因）。

**为什么不再叠一个「小时数 TTL」**（用户问过「还是要对TTL时间进行核验？」）：
它读的是**同一张表同一行**，只是把「在没在收盘之后」换成「距今几小时」——
**同一个来源的两种度量，不是第三个独立因子**，而且更粗（**墙钟** vs **有没有开过盘**）。
实测代价（假设周五 17:30 扫过）：

| 时刻 | age | 距最近收盘 | ②记账因子 | 再叠 24h 会怎样 |
|:--|--:|--:|:--|:--|
| 周五 20:00 | 2.5h | 5.0h | 过 | 过 |
| 周六 10:00 | 16.5h | 19.0h | 过 | 过 |
| **周日 20:00** | 50.5h | 53.0h | 过 | **✗ 拦 → 无用全查** |
| **周一 08:30 盘前** | 63.0h | 65.5h | 过 | **✗ 拦 → 无用全查** |

周末与周一盘前**根本没有新数据**（上次收盘是周五 15:00，之后一直没开过盘），
叠加小时阈值会**用更钝的刻度否决更准的判据**。故**不加**。

**已知残余**（写在这里免得日后当 bug）：判据②无法区分「那次全查里**某只 code 失败了**」。
那只票会落后到**下一个交易日收盘**（TTL 到期、走常规路径时补上）。失败在**当时那一轮**
是报出来的（`stats['errors']`），不是静默的。

**省了什么**：一轮「无事可做」的全量，从 **~40 s**（18 个集合 × 5,575 次 `last_bar`）
降到 **~1 s**（18 次探针）。

**它会不会跨交易日延续？不会**（用户 2026-10-09 要求验这一点）—— 因为**新的收盘会让
`since_close` 归零**，条件自然翻假。**现场演示**（真签到记录 `etf_60min`，真交易日历，
只换时钟）：

| 时刻 | 快路径 | 为什么 |
|:--|:--|:--|
| 周五收盘后（真实）| **跳过** | 收盘后全查过 + 库里已有那批 |
| 周六 10:00 | **跳过** | 周末没开过盘 ⇒「最近一次收盘」仍是**周五 15:00** |
| **周一 10:00 盘中** | **不跳** | 分钟频率 ⇒ 判据① 拦住快路径；常规路径的 TTL 也过期 ⇒ **去取周一的分钟线** |
| 周一 15:30 收盘后 | **不跳** | 新收盘 ⇒ `since_close` 归零 ⇒ 去取周一那批 |

⚠️ **`day` 频率在周一盘中仍会跳，而且那是对的** —— 盘中不写当天日线（P20），
到 15:00 之前都没活干。**这个不对称是刻意的**，用例
`TestFastPathDoesNotSurviveTheNextSession.test_day_fast_path_still_skips_intraday` 钉着它。

**再追加（同日，冷启动改成「核水位」）**：用户 2026-10-09 实报 —— 删掉签到记录后，
`stock_1min` 等**没有记录的集合各跑一遍全量真取**，而数据早已到 15:00 ⇒ **纯重复劳动**
（约 8 分钟/集合 × 15 个集合）。

**改动**：`save_kline_tdx` 里 `cold_start = kline_sweep_age_hours(...) is None`，
`allow_skip` 的条件由
```python
allow_shortcircuit(name, now=_now)          # 无记录 ⇒ False ⇒ 全量真取
```
改成
```python
allow_shortcircuit(name, now=_now) or cold_start
```
即：**无记录时也允许逐只跳** —— 因为本轮本来就会走 ④，**对全宇宙每只 code 核一次水位**
（~5,575 次 `last_bar`，零连接，约 8 秒），那本身就是「每只 code 都到前沿了」的**证据**，
与"真取一遍"等价（真取的结果也是各票水位停在原处）。

⚠️ 这条**推翻了 D25 前面写的「从没扫过（`None`）＝不允许」**。

**为什么安全**（三条都在代码里）：
1. **没数据的 code（`ts is None`）永远不会被跳** ⇒ **全新集合照旧全量真取**；
2. 探针探不到前沿（集合停滞）⇒ 两支都退成全量；
3. **有记录之后 TTL 照旧到期强制真取** ⇒ 兜底网只是**晚一个 TTL** 触发，不是消失。

**记账条件也跟着补了一支**（`not allow_skip or cold_start`）：冷启动核完**必须记账**，
否则下次又是冷启动 ⇒ 永远核水位、永不真取。
而「TTL 新鲜 + 按水位跳」那一次**仍然不记账**（记了 TTL 会被无限推后）。

**真机验证**（`stock_1min` 三只票）：**3/3 核出、零写入、零连接**
（把开跑时的北交所探针也挡掉后 `new_api` 调用数为 0；那 1 次连接与集合无关）。
