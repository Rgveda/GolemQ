# D90. `--review` 盘中带 realtime 合成 + 收盘后重复确认

- **编号**：D90
- **日期**：2026-11-23
- **代码**：`pipeline/review/pipeline.py`
- **测试**：`test_cases/pipeline/`（70 条相关用例）

## 背景

用户发现「盘中 `--review` 跑得飞快」。查实不是优化生效，而是**没有目标可算**：

`_fetch_frames` 三处取数全是 `realtime=False`，只读 `stock_60min` / `stock_day`；
而盘中这两个集合里**还没有当天**的 bar（`--save` 收盘后才写，tick 订阅写的是
`realtime_YYYY-MM-DD` 这个独立集合）。于是：

* `_targets` 返回空 ⇒ 每码只剩「取数 ~0.6s + 扫目标 ~0.3s」⇒ 2,000 码几分钟跑完；
* **盘中跑等于空转**，拿到的仍是上一交易日的状态。

## 两条改动

### ① 取数带 realtime —— **实测后回退**（见文末「实测发现」）

`_fetch_frames` 的 day / 60min / 15min 一度改成 `realtime=True`：

* 盘中 ⇒ 历史 + `realtime_YYYY-MM-DD` 的 L1 tick **合成**出当天已走出的 bar
  （`kline83._merge_realtime`，写侧是 `--sub`）；
* 收盘后 ⇒ 与不带 realtime **同速**：`_merge_realtime` 有两道短路门
  （集合不存在 / 历史不落后 ⇒ 一次 `list_collection_names()` 约 1ms）。

⚠️ **实测后已回退为 `realtime=False`** —— 合成出来的 **volume 差 3500 倍**
（见文末「实测发现」）。开关保留在代码里、注释写明原因，修好合并器量纲后再打开。

### ② 收盘后重复确认：`recheck_days = 1`

盘中写进去的 10:30 / 11:30 / 14:00 是**半根 bar**（当日尚未走完）。收盘后必须
用完整 bar 重算覆盖。`ReviewOptions.recheck_days` 默认从 `0` 改为 **1**：
`missing_targets` 会把「最近 1 个自然日内已持久化」的行也纳入重算。

字段原本就有（`--recheck-days` 只在 `cli.internal` 暴露），这里只改默认值 ——
不新增开关。

## 实测

```
as_of 2026-11-23 15:00    recheck_days 1
000711: day 帧 2354 / 60min 9323 / 15min 34907
        目标  day=3, 60min=9, 15min=41        （改前 day=1, 60min=4, 15min=24）
600519: 目标  day=3, 60min=9, 15min=47
```

多出来的就是「最近一天的复核窗口」。代价：每码多算 2 天日线 + 5 根 60min
（≈ 2s/码），相对单码 45 分钟的回填可忽略。

## 使用口径

| 时间点 | 行为 |
|:--|:--|
| 盘中（09:30–15:00） | 计算并落库当天**已走出**的 bar（半根） |
| 15:00 之后再跑一次 | `recheck_days=1` 把最近一天的行重算覆盖 ⇒ **最终确认值** |

⚠️ 盘中那几次落库的值是「当时可见」的快照，**收盘后必须再跑一次**才是当日终值。
若某天没跑收盘后那次，库里留下的是当天最后一次运行时的半根快照 ——
`--recheck-days` 可以更大（如 3）以覆盖漏跑的日子，但会相应多算。

## 实测发现：tick 合成的 **volume 量纲是错的**（因此 ① 已回退）

先纠正一条旧记录：本机 `golemq_stock_cn_realtime` **不是空的** ——
25 个 `realtime_*` 集合，`realtime_2026-11-23` 有 **2,414,237 行**。

把 `end` 截到 2026-11-20、开 `realtime=True` 实测 000711：

| 项 | 值 |
|:--|:--|
| 合成出今天 14:00 / 15:00 两根 | ✅ 价格对（收盘 4.25，与日线一致） |
| 上午 10:30 / 11:30 | ❌ 没有（tick 集合当天从 13:21 才开始） |
| **14:00 的 volume** | **9.77e9** —— 而当天日线总量只有 **2.75e6**（**3500 倍**） |
| tick 字段 | `amount` 是**累积值**、**没有 `volume`** |

合并器把 tick 的**累积 amount** 当成区间量累加 ⇒ volume/amount 全错。
ChipDist / Renko 量能 / 换手率相关列都会吃 volume，所以 `realtime=True`
**已回退为 `realtime=False`**。

### 要开实时，先修合并器的量纲

`_merge_realtime` → `GQ_fetch_stock_min_realtime_adv` 里按 bar 区间取
`amount_end - amount_start`，再用该区间的 vwap 反推 `volume = Δamount / vwap`；
并且要注意 `if_fq`：历史是 **qfq**、tick 是**原始价**，除权日两者不同源。
修完并逐值对拍（用 `--save` 已落库的同一根 bar 做基准）之后再打开。

## 遗留

* ① 已回退，等合并器量纲修好再开；
* ② `recheck_days=1` 保留 —— 它与 realtime 无关，收盘后再跑一次能覆盖掉
  当天最后一次运行的半根快照。
* 盘中是否会与 `--save`（15:00 写历史集合）冲突，取决于两者先后：
  `--save` 先写 ⇒ realtime 合并那步会因「历史不落后」直接跳过。
