# D23. 服务器选择：**每 worker 线程各粘一台 + 随机起点**（分布式）

- **编号**：D23
- **日期**：
- **索引**：[DECISIONS.md](../../DECISIONS.md) —— `grep D23 DECISIONS.md`，或直接开这个文件

**决定**（2026-10-09）：`TdxSource._host_order()` = **本线程上次成功的那台优先**
+ 其余**随机打散**。`new_api()` 成功时把该台记进 `self._local`（`threading.local`）。

**为什么不是全局粘一台**（D21 的原做法）：所有 worker 会**挤到同一台** ——
实测 60 次连接**全打** `124.71.9.153`。代价有两个：
① 那台负载陡增，**反而更容易进入「不应答」的相位**（本机实测同一台一会 0.2s、
一会 >10s）；② 单台抖动就拖慢全体。

**为什么不是纯随机**：每次都有 `1/台数` 的概率踩坏服、白等一个超时（D21 实测 10s）。
66 台里坏 1 台时，33,474 次 ≈ 500 次 × 10s ≈ **83 分钟**白等。

**正解是两者都要**：新线程用**随机起点**（把并发 worker 散开），之后**粘住自己那台**
（不再从表头重试）。

实测（4 worker × 3 次）：
```
worker0: 122.51.120.217 ×3     worker2: 117.34.114.17 ×3
worker1: 49.232.15.141 ×3      worker3: 180.153.18.172 ×3
```

### TCP 连接的实测账（回答「会不会占用过多」）

* **连接是及时关的** ✓：`_fetch_docs` 的 `finally: api.disconnect()`。
* 但**客户端主动关必然留 TIME_WAIT** —— 实测 60 次 `new_api()+disconnect()`
  → **恰好 60 个 TIME_WAIT**（1:1）。
* 本机动态端口 **49152–65535 = 16,384 个**（Hyper-V/WSL 挖走约 350，剩 ~16,032），
  `TcpTimedWaitDelay` 未设 → 默认 **120s**。
* 稳态占用 = **连接速率 × 120s**。全量 `--save tdx` 有 **33,474** 次连接：
  | 全程耗时 | TIME_WAIT 稳态 | 占端口范围 |
  |---:|---:|---:|
  | 20 分钟 | ~3,350 | 21% ✓ |
  | 10 分钟 | ~6,700 | 42% ✓ |
  | 5 分钟 | ~13,400 | **84% ⚠️** |

  即：**跑得越快越危险**。并发上限由 `--save-jobs`（默认 4）决定，不是连接数上限的来源。

**没做的一件事（有意）**：**没有**加「连接复用」。`PITFALLS.md` P3b 明写 pytdx
一次失败调用会**毒死整条连接**（之后静默返回 None），每 task 一条新连接正是它的
处置办法。复用能把 33,474 次连接降一个数量级，但会重新引入那个静默污染 ——
**要做必须先想清楚怎么检出「连接已废」**，不在本次范围内。
